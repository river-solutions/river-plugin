# River Dynamic Site

A lightweight web server that runs a DuckDB model on demand and displays the results as interactive charts. A user selects a scenario from the UI; the server patches the SQL script with the scenario's parameters, executes DuckDB, reads the output CSV, and streams the data back to the browser.

---

## Prerequisites

| Tool | Version | Notes |
|------|---------|-------|
| [Node.js](https://nodejs.org) | 18+ | DuckDB is installed by `npm install` (`@duckdb/node-api`) |

---

## Installation

```bash
git clone <repo-url>
cd river-dynamic-site
npm install
```

## Setting up a model

### 1. Create the model directory

Point `config.json` at any directory with `modelDir`. The path is relative to the project root.

```json
{ "modelDir": "./model" }
```

### 2. Generate the contents of the `model` directory

The files in this directory are generated by River when using the "Export to SQL" feature. The requirements set below are automatically satisfied by the bundle of files generated. They can be copied as-is to the directory created above.

#### File `script.sql`

All paths in `script.sql` (e.g. `read_csv(...)`) are **relative to `modelDir`**, because the server changes its working directory to `modelDir` at startup.

The script declares scenario parameters as DuckDB `SET VARIABLE` statements at the top, one per line, in this exact format:

```sql
SET VARIABLE node_104_setpoint = 'Ambitious';
SET VARIABLE node_656_setpoint = '-4.4%';
```

The server replaces the quoted value with the scenario's value before running. Lines that have no matching scenario parameter are left unchanged, so their default value is used.

The script writes its outputs to CSV files under `outputs/` (relative to `modelDir`):

```sql
COPY some_result TO 'outputs/Out_my_table.csv' (HEADER, DELIMITER ',');
```

#### File `scenario_definitions.json`

This contains an array of scenario objects. Each parameter key matcesh a variable name in `script.sql`. 

> Warning: a `null` indicates an assumption parameter that has not been set. The server or front-end should react to this situation by marking it as an invalid scenario as it will cause errors when running the duckdb script.

```json
[
  {
    "scenario": "Baseline",
    "parameters": {
      "node_104_setpoint": "Current",
      "node_656_setpoint": "-2.0%",
      "node_467_setpoint": null
    }
  },
  {
    "scenario": "Ambitious",
    "parameters": {
      "node_104_setpoint": "Ambitious",
      "node_656_setpoint": "-4.4%",
      "node_467_setpoint": "Exclude Non-CO2"
    }
  }
]
```

The file may be UTF-8 with or without BOM — both are handled correctly.

### 3. Configure outputs in `config.json`

Add one entry per CSV output you want to expose through the API. The `columns` map declares the name and type (`string`, `integer`, or `float`) of each column — the server uses this to cast values when parsing the CSV.

```json
{
  "port": 3000,
  "modelDir": "./model",
  "scriptFile": "script.sql",
  "scenarioDefsFile": "scenario_definitions.json",
  "outputs": [
    {
      "id": "free_allocation",
      "label": "Free Allocation",
      "file": "outputs/Out_free_allocation.csv",
      "columns": {
        "BM name":    "string",
        "Year":       "integer",
        "Sector":     "string",
        "EUA":        "float",
        "Country":    "string"
      }
    },
    {
      "id": "ets_cap",
      "label": "ETS Cap",
      "file": "outputs/Out_ETS_cap.csv",
      "columns": {
        "Year":  "integer",
        "Cap":   "float",
        "Phase": "integer"
      }
    }
  ]
}
```

## Running the server

```bash
npm start
# → River Dynamic Site running at http://localhost:3000
```

Open `http://localhost:3000` in a browser. Click a scenario button to run the model and display the chart.

## API reference

### `GET /api/scenarios`

Returns the list of scenario names defined in `scenario_definitions.json`.

```json
["Baseline", "Ambitious", "Conservative"]
```

### `GET /api/outputs`

Returns the outputs declared in `config.json`, including their available column names.

```json
[
  { "id": "free_allocation", "label": "Free Allocation", "columns": ["BM name", "Year", "EUA", ...] },
  { "id": "ets_cap",         "label": "ETS Cap",         "columns": ["Year", "Cap", "Phase"] }
]
```

### `POST /api/run`

Patches `script.sql` with the scenario's parameters, runs DuckDB, and returns data from the requested output.

**Request body**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `scenario` | string | yes | Must match a name in `scenario_definitions.json` |
| `output` | string | yes | Must match an `id` in `config.json` `outputs` |
| `columns` | string[] | no | Subset of columns to return. Omit to return all. |
| `filters` | object | no | Key/value pairs applied server-side, e.g. `{ "Country": "Austria" }` |

**Response**

```json
{
  "data":     [ { "BM name": "Hot metal", "Year": 2025, "EUA": 3140572.8 }, ... ],
  "elapsed":  "2.1",
  "scenario": "Ambitious",
  "output":   "free_allocation"
}
```

**Error responses** use standard HTTP status codes with `{ "error": "..." }`.

## Browser API client (`river-api.js`)

Any HTML page served by this server can include the client library and avoid writing raw `fetch` calls.

```html
<script src="/river-api.js"></script>
<script>
  const api = new RiverAPI(); // defaults to same origin

  // List scenarios
  const scenarios = await api.scenarios();

  // List outputs
  const outputs = await api.outputs();

  // Run model and fetch a subset of columns, filtered server-side
  const result = await api.run('Ambitious', 'free_allocation', {
    columns: ['BM name', 'Year', 'EUA', 'Country'],
    filters: { Country: 'Germany' },
  });

  console.log(result.data);    // array of row objects
  console.log(result.elapsed); // "2.1"
</script>
```

`RiverAPI` also works as a CommonJS or ES module if you import it server-side or in a bundled frontend.

## Concurrency and production considerations

The server is designed for **single-user or low-concurrency internal use**. It uses an in-memory flag (`isRunning`) to reject concurrent model runs with HTTP 429. This is adequate for a small team where runs rarely overlap, but has the following limitations in a production environment:

**The flag is process-local.** Under a load balancer with multiple Node processes, each process has its own flag. Two simultaneous requests routed to different processes will both run DuckDB and race to write the output CSV — producing corrupt or mixed results.

**The output files are shared globals.** The output CSVs in `outputs/` are fixed paths. Even within a single process, any bypass of the 429 guard would let two runs interfere.

**429 is a hard rejection, not a queue.** A second user gets an error rather than waiting for the first run to finish.

For a genuinely concurrent deployment, the required changes are:

| Problem | Solution |
|---------|----------|
| Shared temp script | Generate a UUID per request; write `_temp_<uuid>.sql` and a matching temp output directory; delete both after the run |
| Multi-process locking | Use a distributed lock: Redis `SET NX` (via [ioredis](https://github.com/redis/ioredis)), or a PostgreSQL advisory lock |
| No queuing | Add a job queue ([BullMQ](https://bullmq.io/) backed by Redis); return a job ID immediately, let clients poll `GET /api/jobs/:id` |
| Repeated identical runs | Cache results keyed by `scenario + output` (or a hash of the patched SQL) with a short TTL |
