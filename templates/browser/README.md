# River Dynamic Site

A static website that runs a DuckDB model **in the browser** (DuckDB-WASM) and displays the results as interactive charts. A user selects a scenario; the page patches the SQL script with the scenario's parameters, runs it in DuckDB-WASM against the model's input CSVs, and charts the output. There is no backend: `public/` can be hosted on any static web server, on any platform.

---

## Prerequisites

| Tool | Version | Notes |
|------|---------|-------|
| [Node.js](https://nodejs.org) | 18+ | Optional: only for `npm start`. On Windows, `start.bat` serves the site without Node. Any static web server also works. |
| A modern browser | | Chrome, Edge, Firefox or Safari. DuckDB-WASM is loaded from the jsDelivr CDN. |

## Setting up a model

### 1. Create the model directory

Point `public/config.json` at the model with `modelDir`. The path is relative to `public/`.

```json
{ "modelDir": "model" }
```

### 2. Generate the contents of the `model` directory

The files in this directory are generated by River when using the "Export to SQL" feature. The requirements set below are automatically satisfied by the bundle of files generated. They can be copied as-is to the directory created above.

#### File `script.sql`

All paths in `script.sql` (e.g. `read_csv(...)`) are **relative to `modelDir`** and must start with `inputs/` or `outputs/` (`inputs\` is fine too). The browser fetches every `inputs/…` file it finds in the script and loads it into DuckDB-WASM's in-memory filesystem; `outputs/…` files are written in memory.

The script declares scenario parameters as DuckDB `SET VARIABLE` statements at the top, one per line, in this exact format:

```sql
SET VARIABLE node_104_setpoint = 'Ambitious';
SET VARIABLE node_656_setpoint = '-4.4%';
```

`river-api.js` replaces the quoted value with the scenario's value before running. Lines that have no matching scenario parameter are left unchanged, so their default value is used.

The script writes its outputs to CSV files under `outputs/` (relative to `modelDir`):

```sql
COPY some_result TO 'outputs/Out_my_table.csv' (HEADER, DELIMITER ',');
```

#### File `scenario_definitions.json`

This contains an array of scenario objects. Each parameter key matches a variable name in `script.sql`. 

> Warning: a `null` indicates an assumption parameter that has not been set. The front-end should react to this situation by marking it as an invalid scenario as it will cause errors when running the duckdb script.

```json
[
  {
    "scenario": "Baseline",
    "parameters": {
      "node_104_setpoint": "Current",
      "node_656_setpoint": "-2.0%",
      "node_467_setpoint": null
    }
  },
  {
    "scenario": "Ambitious",
    "parameters": {
      "node_104_setpoint": "Ambitious",
      "node_656_setpoint": "-4.4%",
      "node_467_setpoint": "Exclude Non-CO2"
    }
  }
]
```

The file may be UTF-8 with or without BOM — both are handled correctly.

### 3. Configure outputs in `public/config.json`

Add one entry per CSV output you want to expose through the API. The `columns` map declares the name and type (`string`, `integer`, or `float`) of each column — `river-api.js` uses this to cast values when reading the output.

```json
{
  "port": 3000,
  "modelDir": "model",
  "scriptFile": "script.sql",
  "scenarioDefsFile": "scenario_definitions.json",
  "outputs": [
    {
      "id": "free_allocation",
      "label": "Free Allocation",
      "file": "outputs/Out_free_allocation.csv",
      "columns": {
        "BM name":    "string",
        "Year":       "integer",
        "Sector":     "string",
        "EUA":        "float",
        "Country":    "string"
      }
    },
    {
      "id": "ets_cap",
      "label": "ETS Cap",
      "file": "outputs/Out_ETS_cap.csv",
      "columns": {
        "Year":  "integer",
        "Cap":   "float",
        "Phase": "integer"
      }
    }
  ]
}
```

## Running the site

Locally, pick one:

- **Windows, no install:** double-click `start.bat`. It starts a small PowerShell server and opens the browser. Close the window to stop it.
- **Node:** `npm install` once, then `npm start`.
- **Mac/Linux:** `python3 -m http.server 3000 -d public`.

Then open `http://localhost:3000` in a browser (`port` in `config.json` sets the port). Click a scenario button to run the model and display the chart.

### Sharing as a zip (Windows, no install)

Zip `start.bat`, `serve.ps1` and `public/`. You don't need `server.js`, `package.json` or `node_modules`. The recipient unzips the folder and double-clicks `start.bat`.

- Windows may show a security warning for files that came from an email or download. Click **Run**, or right-click the zip → Properties → **Unblock** before extracting.
- Viewers still need internet access, because DuckDB-WASM and Chart.js load from a CDN. The first run takes longer while DuckDB-WASM downloads.
- Everything in `public/model/` is readable by the recipient.

To deploy, upload the contents of `public/` to any static host (IIS, nginx, Azure Static Web Apps, GitHub Pages, S3…). Opening `index.html` straight from disk (`file://`) does **not** work, because the browser blocks `fetch` and workers there.

## Browser API client (`river-api.js`)

```html
<script src="/river-api.js"></script>
<script>
  const api = new RiverAPI(); // config.json next to the page; or new RiverAPI('https://host/site')

  // List scenarios (names from scenario_definitions.json)
  const scenarios = await api.scenarios();      // ["Base case", "Optimistic", ...]

  // List outputs declared in config.json
  const outputs = await api.outputs();          // [{ id, label, columns: [...] }]

  // Run the model and fetch a subset of columns, filtered in SQL
  const result = await api.run('Optimistic', 'beds', {
    columns: ['DRG Classification', 'Year', 'Bed_gap'],
    filters: { Year: 2030 },
  });

  console.log(result.data);    // array of row objects
  console.log(result.elapsed); // "1.2" (seconds)
</script>
```

Errors are thrown as `Error` objects (unknown scenario/output, DuckDB errors, or `Model is already running, please wait.` if `run()` is called while a run is in progress).

## Things to know

- **The model is public.** Everything in `public/model/` (the SQL script and the input CSVs) can be downloaded by anyone who can open the site. Don't deploy confidential inputs this way.
- **Runs use the viewer's machine.** Each run takes the viewer's CPU and memory (a browser tab caps DuckDB-WASM at about 4 GB). Small and medium models run in about a second.
- **No concurrency limits.** Each viewer runs their own copy of the model, so there is no shared state and no server to scale.
- **Internet access is needed** to load DuckDB-WASM from `cdn.jsdelivr.net` (version pinned in `river-api.js`).
